# INT8 Sparse Systolic MLP Accelerator with On-Chip Training

A Verilog hardware accelerator for a small neural network (MLP, 64 → 16 → 10,
8×8 handwritten digits) with two parts:

1. **Inference**: two weight-stationary systolic arrays with INT8 arithmetic
   and pruned (sparse) weights. Processes 1 image per clock cycle.
2. **Training**: an on-chip engine that runs the forward pass,
   backpropagation and SGD weight updates for both layers. Python calls it
   through a plug-in class.

Both parts are verified **bit-exact** against Python fixed-point reference models.

| | Result |
|---|---|
| Inference accuracy (INT8, pruned) | 96.67% on 360 held-out images, 0 mismatches vs. golden model |
| Inference throughput / latency | 1 image/cycle, 84 cycles |
| Sparsity | 387 of 1,184 PEs need a multiplier (70% / 50% pruned) |
| On-chip training | 14 cycles per SGD step (16,8,10 lanes), 96.94% accuracy, weights bit-identical over 21,555 steps |
| Training speedup | 7.7–15.4× vs. optimised C (-O3) at batch size 1, at an estimated 100–200 MHz |

## Part 1: Inference accelerator

```
                skew buffer               layer 1: 16 chains x 64 PEs
 x[0..63] ─▶ x0 ─────────────▶ b_i ─▶[PE i,0]─▶[PE i,1]─▶ … ─▶[PE i,63]─▶ requant ─▶ h_i
             x1 ─(1 reg)─────────────────┘ ↑          ↑                      (ReLU, int8)
             x63─(63 regs)──────────────────────────────────────┘
                                          layer 2: 10 chains x 16 PEs ─▶ argmax ─▶ class
```

* One chain per output neuron. **PE(i,j)** holds weight w[i][j] and computes
  `psum += w * x[j]`. The partial sum moves one PE per clock.
* The **skew buffer** delays x[j] by j cycles, so it meets every chain's
  partial sum exactly at PE j.
* The **bias** is the chain's initial partial sum, so it needs no extra adder.
* Every stage is registered, so a new image enters **every clock cycle**.

### Memory architecture

```
 host ──▶ ping-pong image buffer ──512 b/cycle──▶ mlp_core ──▶ result RAM ──▶ host
          bank0 | bank1 (128 images each)                      (class per tag)
```

* One image is one 512-bit word, so the core gets a full input vector every cycle.
* The host fills one bank while the core drains the other, so loading
  overlaps compute.
* Layer 1 feeds layer 2 through a pipeline register; no inter-layer memory is needed.
* The result RAM has its own host read port, so readout never stalls the array.

### Optimisations

| Optimisation | How | Effect |
|---|---|---|
| INT8 datapath | int8 weights, 0..127 activations, integer-only requant (`× M >> SH`) | 8×8 multipliers, no floating point |
| Minimum accumulator width | worst-case bound \|b\| + Σ\|w\|·127, computed offline | 19 / 17 bits instead of 32 |
| Sparse weights | magnitude pruning + retraining with a fixed mask; a PE with w = 0 becomes a bare register | 387 of 1,184 PEs need a multiplier |
| Constant weights | weights are parameters, so synthesis reduces multiplies to shift-adds | no weight memory or reads |

## Part 2: On-chip training engine

```python
from fpga_trainer import FpgaTrainer
hw = FpgaTrainer(lanes=16, l2_lanes=8, bp_lanes=10)
params, cycles = hw.train(init_params, Xq, y, order)
```

The backend is cycle-accurate RTL simulation (Verilator, or Icarus Verilog if
Verilator isn't installed). A board backend would send the same buffers over
MMIO/DMA.

### How it works

* **Parallel within a sample.** Each SGD step needs the weights from the
  previous step, so the engine parallelises inside one sample: P inputs ×
  16 neurons (layer 1), Q inputs × 10 neurons (layer 2), and R rows × 16 (backprop).
* **Fused update + forward pass.** Sample n's weight update and sample n+1's
  forward pass sweep the weights in the same order. Each weight is read once,
  updated, written back and immediately used for the next sample.
* **Weight storage.** W1 lives in RAM banks, since it's never read transposed. W2
  lives in registers, because forward reads columns and backprop reads rows.
* **Prefetch.** The next sample is fetched during backprop.
* **Fixed point** (spec: `train/hwref.py`). INT8 activations, 16-bit forward
  weights, 32-bit master weights (Q.20), 16-bit errors, lr = 2⁻⁷, MSE loss.

### Benchmark (15 epochs = 21,555 SGD steps)

| Engine (P,Q,R) | Cycles / step | Multipliers | vs C -O3, batch 1 | vs NumPy mini-batch 32 |
|---|---|---|---|---|
| 1,1,1 | 97 | 68 | 1.1–2.2× | 2.0–4.1× |
| 8,4,5 | 21 | 416 | 5.1–10.3× | 9.4–18.8× |
| **16,8,10** | **14** | **832** | **7.7–15.4×** | **14–28×** |
| 64,16,10 | 10 | 2,528 | 10.8–21.6× | 20–40× |

* Speedup ranges are for an estimated 100 → 200 MHz clock.
* CPU baseline: Intel Xeon @ 2.8 GHz, single thread, 1.08 µs/sample for the C version.
* Including data loading and weight readback lowers the speedups by 3–12%.
* Full table: `train/results.md`.

**Why it's faster:** each step is about 2,500 multiplications. The CPU averages
under 1 multiply per cycle on these tiny, sequential per-sample updates, while
the engine does about 180 per cycle in parallel.

## Limitations and next steps

* **Fmax is not measured yet.** Hardware time is cycles ÷ an assumed 100–200 MHz.
  Run synthesis to get the real clock.
* The advantage depends on **batch-size-1 SGD**. At large batch sizes, CPUs and
  GPUs vectorise well and a GPU would win.
* In the inference core, the 10-way argmax and the requant multiplier are single
  combinational stages; pipeline them before pushing Fmax.
* The arrays are fully unrolled. Larger layers (e.g. 784 inputs) would need
  time-multiplexed or tiled arrays with weights in BRAM.
